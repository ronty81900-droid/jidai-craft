# 指示: 特殊アイテム16種の絵を作り直す（高解像度・古地図風）

Minecraft のイベント「時代クラフト」で、ガチャから出る**特殊アイテム16種**の絵を
高解像度で作り直してください。既にあるUIと同じ**古地図風**で揃えます。

作業場所は、この企画の置き場の直下（`README.md` がある所）です。

| 種類 | 何枚 | 大きさ | 今の大きさ |
|---|---:|---|---|
| **特殊勝利アイテム**（集める5種） | 5 | **512 × 512** | 16 × 16 |
| **特殊効果アイテム**（遺物11種） | 11 | **256 × 256** | 64 × 64 |

## 2. ★ 高解像度で一番大事な決まり

**Minecraftはこの絵を 16×16 に縮めて出す場面があります。**
そのまま細かく描くと、**縮めた時に潰れて前より汚くなります。**

実測しました。

```
512 を 16 に nearest で縮めると、262,144 画素のうち 256 個（0.10%）しか拾われない
256 を 16 に nearest で縮めると、65,536 画素のうち 256 個（0.39%）しか拾われない
```

前回の 64×64 は、縮めても形が崩れませんでした（面積 38%→37%、色数 11→11）。
**粗い格子に乗せて描いてあったから**です。同じ作り方を、もっと細かい格子で続けます。

### やり方

1. まず **16 × 16 の下絵**を描く。これが「縮めた時に見える姿」になる
2. 下絵を **32倍**（512の場合）または **16倍**（256の場合）に引き伸ばす
3. その格子の中に細部を描き込む。**下絵の色を、格子の中心では動かさない**

守る条件は2つです。両方 機械で確かめます。

| | 条件 | なぜ |
|---|---|---|
| ① | 高解像度の絵を nearest で 16×16 に縮めた物が、**下絵と1画素も違わない** | MODの画面（`Kazari.aitem`）は nearest で縮めて貼るため |
| ② | 各格子（32×32 または 16×16）の**平均色が下絵の色に近い**（各成分の差 40以内、アルファの差 25%以内） | バニラの描画は平均で縮める（ミップマップ）ため |

①は「格子の中心の1画素」、②は「格子ぜんたいの色味」を見ています。
どちらも満たすと、**縮めても下絵の姿になり、大きく出す場面では細部が出ます**。

### 512 が効く所と効かない所

| 場面 | どう縮む | 512 は効くか |
|---|---|---|
| 手に持つ・地面に落ちている | バニラの地図帳（平均・ミップマップ） | **効く**。配信で大きく映る |
| 持ち物欄・ホットバー | 16論理px・平均 | 少し効く |
| こちらの古地図の画面 | 16論理px・**nearest** | **効かない**。①の条件が守り |

## 3. 古地図風の決まり

**色の正本は `clientmod/nouhin/v6/DESIGN_SPEC.md` の「共有パレット」52色です。**
ここから使ってください。足したい色があれば `DESIGN_SPEC.md` に名前と理由を書いてください。

前回の作図規約を引き継ぎます。

- 背景は `#00000000`。**不透明度は 0 か 255 だけ**。ぼかし・発光・半透明・グラデーションは無し
- **アンチエイリアスを掛けない。** 中間色を作らない
- 完全に透明な画素の RGB は `0,0,0`
- 輪郭は暗い `outline`（`#102329`）。**素材面の内部には輪郭色を使わない**（内部は色面の境界だけ）
- 光源は**左上**。最高輝度 `highlight`（`#F5DE9B`）は**1枚に1か所のまとまりだけ**
- 経年の傷・欠け・煤は**1枚に1か所だけ**
- 外周に透明の余白を取る（512なら 24〜32px、256なら 12〜16px）
- **読める文字・数字・ロゴ・実在メーカーのUIは描かない**
- 角は直角。丸めない

色数は 1枚あたり **64色以内**にしてください（前回は 8〜13色でした。
解像度が上がったぶん増えて構いませんが、増やすほど古地図らしさが薄れます）。

時代が上がるほど**素材が変わって見える**ようにしてください
── 鉄器は石と革、中世は真鍮と羊皮紙、近代は鉄と煤、現代は黒い樹脂とガラス。
色相だけでなく**素材の質**で時代を見せます。

## 4. どう作るか

**手で描かないでください。絵を吐くスクリプトを書いてください。**

前回の納品も同じ作り方です（v6 の DESIGN_SPEC に
「すべて最初から64×64の整数ピクセル形状として構成し、写真・生成画像・高解像度原画を
縮小していません」と書いてあります）。

| | |
|---|---|
| 置き場所 | `clientmod/tools/tokushu_e_tsukuru.py` |
| 吐き先 | `clientmod/nouhin/v7/` |
| 動かし方 | `python clientmod/tools/tokushu_e_tsukuru.py` |

守ること。

- **2回動かしたら同じ byte が出る**こと。乱数を使うなら種を固定する
- 名前・ファイル名・番号は **`Shouri.java` から読む**。スクリプトに直書きしない
- 色は **v6 の DESIGN_SPEC から読む**。スクリプトに16進を直書きしない
  （足す色だけ、スクリプトの先頭で1か所にまとめて定義する）
- **下絵（16×16）も同じスクリプトが吐く**。あとから手で作らない

## 6. 検査

`tests/tokushu_e_kakunin.py` を書いて、動かして、**結果の数字をそのまま報告**してください。
このプロジェクトの他の検査（`tests/*_kakunin.py`）と同じ形にしてください
── `[PASS] 名前` / `[FAIL] 名前  理由` を1行ずつ出し、最後に件数を出します。

見る物。

1. 16枚あるか。ファイル名が `Shouri.java` と1つも違わないか
2. 大きさが 512 / 256 の指定どおりか
3. **①縮めたら下絵と1画素も違わないか**（§2）
4. **②各格子の平均色が下絵に近いか**（§2）
5. アルファが 0 か 255 だけか
6. 完全に透明な画素の RGB が `0,0,0` か
7. 1枚の色数が 64色以内か
8. 使った色が v6 の共有パレットにあるか（`DESIGN_SPEC.md` で断った新色を除く）
9. `highlight`（`#F5DE9B`）が1枚に**1つの連結したまとまり**だけか
10. 素材面の内部に `outline` が入っていないか
11. 外周の透明余白が足りているか
12. プレビューが本番の nearest 縮小と1画素も違わないか
13. `manifest.json` の sha256 と寸法が実物と合っているか
14. スクリプトを2回動かして byte が一致するか

★ **書いた検査は、わざと壊して落ちることを確認してください。**
　 このプロジェクトの流儀です。通ることを確かめただけでは、
　 検査が実は何も見ていない場合に気付けません。
　 確認したら**必ず元に戻して**、もう一度通してください。

## 7. 組み込みまでやる

絵を置くだけでは、ゲームには出ません。**組み込みまでが仕事です。**

1. `clientmod/tools/tokushu_moderu.py` の `NOUHIN` と `NOUHIN_IBUTSU` を **v7 に向ける**
2. `python clientmod/tools/tokushu_moderu.py` を動かす
3. 出来上がる物を確かめる
   - `clientmod/tokushu/assets/jidaiui/textures/item/*.png` … 16枚
   - `clientmod/tokushu/assets/jidaiui/models/item/*.json` … 16枚
   - `clientmod/tokushu/assets/minecraft/models/item/paper.json` … 番号の小さい順
   - `clientmod/src/main/java/jidai/ui/Tokushu.java` … `OOKISA` が 512／256 になる
4. `python clientmod/build.py` で jar が通ることを確かめる

★ `Tokushu.java` は **`tokushu_moderu.py` が作ります。手で直さないでください。**
　 `OOKISA` は PNG の IHDR から読むので、絵を差し替えれば自動で追いつきます。

★ `tokushu_moderu.py` は納品の `manifest.json` の sha256 と実物を照合して、
　 違えば止まります。**sha256 は大文字**で書いてください。

## 8. 納品の形

```
clientmod/tools/tokushu_e_tsukuru.py            絵を吐くスクリプト
clientmod/nouhin/v7/
  ├── assets/jidaiui/textures/item/             本番（16枚）
  │     ├── gofu.png  seihai.png  kaizu.png  haguruma.png  tsukinoishi.png   512x512
  │     └── sensha.png … sumaho.png                                          256x256
  ├── shitae/                                   下絵（16枚・すべて 16x16）
  ├── preview/                                  目で見る用（本番を nearest で 1/2 に縮めた物）
  ├── preview_shitae/                           下絵を nearest で 8倍にした物（縮んだ時の姿）
  ├── manifest.json                             1枚ごとの sha256・寸法・使った色
  └── DESIGN_SPEC.md                            使った色の一覧と、この指示文の sha256
tests/tokushu_e_kakunin.py                      §6 の検査
```

`manifest.json` は v6 の物と**同じ形**にしてください。
`files` の各項目に `category: "item_texture"`、`sha256`（大文字）、寸法を入れます。
`tokushu_moderu.py` がこの2つを見ています。

**プレビューは本番の画像を nearest で縮めた物にしてください。** 別に描き起こさないでください。
`tokushu_e_tsukuru.py` が同じ実行の中で吐けば、ずれようがありません。

`DESIGN_SPEC.md` には、**この指示文の sha256** を書いてください。

```bash
python -c "import hashlib;print(hashlib.sha256(open(r'docs\Fable依頼文_特殊アイテム.md','rb').read()).hexdigest())"
```

## 9. 環境（実測済み）

| | |
|---|---|
| Python | 3.14.6 |
| Pillow | 12.2.0 |
| numpy | 2.4.6 |
| OS | Windows 11 |

踏みやすい罠が3つあります。

- **パスに日本語が入っています。** ファイルは UTF-8 で読み書きしてください
- **bash のヒアドキュメントは `\n` や `\\` を壊します。**
  パッチ用のスクリプトは Write で書いてください
- **改行が CRLF のファイルがあります。** 複数行の文字列で検索する時は、
  `chr(13)+chr(10)` が入っているか先に見てください

絵の総量が増えます。5×512² + 11×256² ＝ 約 203万画素で、
バニラの地図帳（アイテムのアトラス）が一段大きくなります。
`build.py` が通っても、実機で起動した時に絵が出るかは別なので、
**起動して持ち物欄で見るまでは「終わった」と言わないでください。**
